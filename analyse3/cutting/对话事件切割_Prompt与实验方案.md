# 对话事件切割：Prompt 与最小实验方案

## 1. 目标

将一个完整的用户与 LLM 对话 session 切分为若干按时间连续、语义单一的对话事件，为后续语义锚点提取和用户记忆聚类提供纯净输入。

切割阶段只处理局部事件边界。相同话题在对话中断后再次出现时，仍然形成新的事件；跨时间的同类事件由后续聚类关联。

例如：

```text
A：讨论用户记忆系统
B：规划日本旅行
A：继续讨论用户记忆系统
```

切割结果为三个连续事件：`A1`、`B`、`A2`。

## 2. 切割单位

边界候选位置建立在语义单元之间，而不是直接建立在 user/assistant turn 之间。

语义单元可以是：

- 一个句子；
- 一个具有独立语义的分句；
- 一个列表项；
- 一段承担独立交互功能的短文本。

每个语义单元保留以下信息：

```json
{
  "unit_id": "u001",
  "message_id": "m001",
  "speaker": "user",
  "text": "帮我设计一个对话切割实验。"
}
```

这样既可以在一个 turn 内部切割，也可以让多个 turn 共同构成一个事件。

## 3. 对话事件定义

一个对话事件是围绕同一个局部交互目标展开的连续语义单元。

边界判断的核心问题是：

> 从当前位置开始，用户是否开启了一个可以相对独立理解的新交互目标？

以下内容通常属于当前事件：

- 对当前问题的追问；
- 澄清或纠正；
- 补充条件和修改要求；
- 对当前内容的举例；
- 完成当前目标所需的步骤。

以下情况通常开启新事件：

- 用户开始新的独立问题或任务；
- 用户转向另一个需要单独处理的对象；
- 用户明确提出新的交互目标；
- 某个话题被其他内容中断后再次出现。

关键词或领域变化只能作为辅助信息，最终依据是用户当前想完成的事情是否发生了变化。

## 4. 单次切割 Prompt

任务规则和数据分别放入 System Prompt 与 User Prompt。System Prompt 在所有样本中保持不变，User Prompt 只承载当前 session 的语义单元。

### 4.1 System Prompt

```text
你负责将用户与 LLM 的对话切分为若干连续、语义单一的对话事件。

一个对话事件围绕同一个局部交互目标展开。当用户开始一个可以相对独立理解的新目标、新任务或新问题时，开启新事件。

追问、澄清、纠正、补充条件、举例，以及完成当前目标所需的步骤，属于当前事件。话题中断后再次出现时，形成新的事件。

所有语义单元按照原始顺序分配到事件中。每个语义单元恰好属于一个事件，每个事件包含连续的语义单元。

输出格式：
{
  "segments": [
    {
      "segment_id": "seg001",
      "start_unit_id": "u001",
      "end_unit_id": "u008"
    }
  ]
}
```

### 4.2 User Prompt

```text
请切割以下对话：

{{units_json}}
```

模型在一次调用中完成整个 session 的切割。输出只描述区间，过滤、主题归类和语义锚点提取在后续阶段完成。

## 5. 输入示例

```json
{
  "session_id": "s001",
  "units": [
    {
      "unit_id": "u001",
      "message_id": "m001",
      "speaker": "user",
      "text": "帮我设计对话切割实验。"
    },
    {
      "unit_id": "u002",
      "message_id": "m002",
      "speaker": "assistant",
      "text": "可以先确定切割标准。"
    },
    {
      "unit_id": "u003",
      "message_id": "m003",
      "speaker": "user",
      "text": "切割结果应该怎么评估？"
    },
    {
      "unit_id": "u004",
      "message_id": "m004",
      "speaker": "user",
      "text": "另外，帮我规划一下日本旅行。"
    }
  ]
}
```

## 6. 输出示例

```json
{
  "segments": [
    {
      "segment_id": "seg001",
      "start_unit_id": "u001",
      "end_unit_id": "u003"
    },
    {
      "segment_id": "seg002",
      "start_unit_id": "u004",
      "end_unit_id": "u004"
    }
  ]
}
```

## 7. 最小实验目标

第一轮实验只回答一个问题：

> LLM 单次直接切割能否产生足够准确、纯净，并适合后续语义锚点提取的对话事件？

## 8. 实验设置

使用本文 Prompt 对测试集中的完整 session 进行单次切割，并与人工标注的事件边界进行比较。

第一轮固定 LLM 模型、温度、Prompt 和语义单元划分方式。实验重点是测量整体切割质量、不同场景下的错误分布，以及预测事件能否作为语义锚点提取的输入。

## 9. 实验数据

建议先构建一个小规模人工标注集：

- 开发集：50 至 100 个 session，用于调整语义单元划分和 Prompt；
- 测试集：100 至 200 个 session，用于最终比较；
- 两名标注者独立标注边界；
- 分歧样本经过讨论或第三人裁决形成最终标签；
- 记录两名标注者边界相差的语义单元数量，用于判断是否需要容差指标。

样本应覆盖：

- 单一主题和多个主题；
- 显式切换和隐式切换；
- 话题中断后回归；
- 一个 turn 内部发生转场；
- 同一项目下的追问、修改和子任务；
- 较短和较长的 session。

## 10. 标注原则

标注者逐一检查相邻语义单元之间的位置，并回答：

> 右侧是否开启了一个可以相对独立理解的新交互目标？

标注结果为：

```json
{
  "after_unit_id": "u003",
  "before_unit_id": "u004",
  "boundary": true
}
```

标注时遵循与 Prompt 相同的事件定义。标注规范和模型 Prompt 使用同一套标准，可以减少任务定义不一致造成的评价偏差。

## 11. 评价指标

### 11.1 边界指标

- 精确 Boundary Precision；
- 精确 Boundary Recall；
- 精确 Boundary F1，作为主要边界指标；
- Boundary F1@±1，作为可选的辅助指标。

部分转场单元可以合理地附着在前一事件或后一事件，因此人工标注边界可能只相差一个语义单元。容差指标用于识别这类接近正确的切割，但不能代替精确 Boundary F1。

是否采用 `±1` 应由人工标注分歧决定：如果标注者的边界分歧经常集中在相邻语义单元，则报告该指标；如果语义单元足够细且边界标注明确，则只使用精确指标。

容差匹配采用一对一匹配，一个预测边界最多匹配一个人工边界，一个人工边界也最多被一个预测边界命中。

### 11.2 整体分段指标

- Pk；
- WindowDiff。

### 11.3 段内纯度

人工抽样检查每个预测事件是否包含两个可以独立形成记忆锚点的交互目标。

段内纯度可以定义为：

```text
纯净事件数量 / 抽检事件总数
```

对于用户记忆场景，漏切会产生混合主题，通常比适度多切更难在后续修复。因此应单独报告漏切数量和过切数量，而不能只看总体 F1。

## 12. 实验步骤

1. 将原始 session 转换为带稳定 ID 的语义单元。
2. 完成人工边界标注并解决标注分歧。
3. 使用固定 Prompt 和固定模型运行 LLM 单次切割。
4. 计算精确边界指标、Pk、WindowDiff 和段内纯度；人工分歧支持时补充 Boundary F1@±1。
5. 分析漏切、过切、话题回归和同 turn 转场错误。
6. 抽样检查预测事件生成的语义锚点是否出现主题混合或上下文缺失。

## 14. 第一阶段结论标准

如果 LLM 单次切割同时满足以下条件，就可以进入后续语义锚点实验：

- 边界指标达到项目设定的可用标准；
- 话题回归和同 turn 转场样本没有出现集中性错误；
- 预测事件具有较高段内纯度；
- 漏切数量处于下游用户记忆提取可以接受的范围。

如果单次切割效果已经足够，保持当前简单方案。只有实验显示明确的问题后，再针对具体错误增加机制。
