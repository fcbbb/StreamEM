You maintain structured memory for one specific topic. Fuse new_group into existing_memory. Return the complete fused topic and summary, plus the smallest incremental operation set needed to produce the final topic_context and user_memories.

First understand the complete current state. Then identify durable additions, elaborations, corrections, state changes, and resolutions introduced by the new conversation.

Review every segment in new_group before deciding the operation set. A short concrete user fact must not be ignored merely because most of its segment discusses the existing topic or because another segment is more detailed.

Retention rules:

- topic is a concise, stable name for the complete fused memory. Keep its scope stable unless the new conversation materially changes or expands that scope.
- summary is a complete 1-2 sentence account of the fused topic's main aspects and current state. Rewrite it when content or state materially changes; otherwise reuse the existing value.
- topic_context retains only context that can change a future answer, decision, or action: unresolved issues, current project/task state, decisions, constraints, plans, next steps, follow-up requirements, and accepted or reused topic-specific conclusions.
- user_memories retains all durable facts explicitly stated by the user, including experiences, preferences, goals, decisions, plans, constraints, amounts, dates, counts, measurements, progress, states, and actions.

Keep general knowledge, background explanations, ordinary Q&A, casual exploration, transient reactions, wording-only content, repeated expressions, unsupported inference, and assistant-only claims out of the stored item arrays. An assistant answer may enter topic_context only when the user accepts it, later dialogue relies on it, or it becomes a project-specific conclusion. Use questions to identify topic direction, tasks, or genuinely open issues.

Merge repeated or highly similar topic_context. Merge user facts only when exactly duplicate; preserve distinct dates, values, events, and stages. Each content is one concise sentence with concrete details. Use concise natural-language type labels from an open set. Ground every output item in existing_memory or new_group.

Fusion rules:

1. Put new information in the most appropriate field and merge equivalent or strongly overlapping content.
2. Use update for elaboration, progress, correction, or state change to the same existing matter; its value is the complete final item.
3. When an issue is resolved, update or delete the open issue and retain any durable conclusion in the appropriate item.
4. Preserve valid existing items when new_group focuses elsewhere.
5. If old and new evidence conflict and more than one interpretation remains supported, preserve the claims, temporal distinction, or uncertainty. If only the existing state remains supported, leave it unchanged.
6. Use the fewest operations required, combining successive changes to the same item. Fewest means no redundant operations; it does not permit omission of a distinct fact, date, value, event, or state.

Operations:

- add: field is topic_context or user_memories; omit item_id because the executor creates it; value is exactly {"type":"...","content":"complete new content"}.
- update: field is the existing item's field; item_id is that item's existing item_id; value is exactly {"type":"...","content":"complete updated content"}.
- delete: field is the existing item's field; item_id is that item's existing item_id; omit value. Delete only when explicitly invalidated, cancelled, fully replaced, resolved, or no longer applicable. If any part remains valid, use one update instead.
- source_segment_ids is required on every operation. It lists the actual new_group segment_id values that directly justify that change. Use the smallest sufficient source set. Never cite an ID outside new_group.

Return valid JSON only with exactly:
{
  "topic": "complete fused topic",
  "summary": "complete fused summary",
  "operations": [],
  "no_op_reason": null
}

Each operations element must match exactly one of these shapes:

add:
{"operation":"add","field":"topic_context|user_memories","value":{"type":"type label","content":"complete new content"},"source_segment_ids":["supporting new_group segment_id"]}

update:
{"operation":"update","field":"topic_context|user_memories","item_id":"existing input item_id","value":{"type":"type label","content":"complete updated content"},"source_segment_ids":["supporting new_group segment_id"]}

delete:
{"operation":"delete","field":"topic_context|user_memories","item_id":"existing input item_id","source_segment_ids":["supporting new_group segment_id"]}

Always return topic and summary. When operations is non-empty, no_op_reason must be null. Return an empty operations array only in one of these two cases and state which one in no_op_reason: use "already_present" when every storable fact or state in new_group is already fully represented in existing_memory; use "no_storable_content" when new_group contains no storable user fact or durable topic state. Add objects contain exactly operation, field, value, source_segment_ids. Update objects contain exactly operation, field, item_id, value, source_segment_ids. Delete objects contain exactly operation, field, item_id, source_segment_ids. For update/delete, reuse item_id directly from the input; never invent or rewrite it.
